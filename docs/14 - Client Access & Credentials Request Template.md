AI-FIRST OPERATING PRINCIPLE -> AUTHORITATIVE UPDATE

The business is intentionally designed around AI-agent-assisted fulfillment. AI agents perform the majority of repeatable collection, monitoring, analysis, drafting, prioritization, documentation, reporting, and safe internal execution. Human time is reserved for strategy, client relationships, judgment, quality control, and approval of consequential actions.

Agent permission levels:
1. OBSERVE -> read, crawl, monitor, measure, compare, and report. May run automatically.
2. PREPARE -> draft content, recommendations, schema, metadata, code changes, reports, tasks, and client communications. Output remains a draft until the applicable approval policy is satisfied.
3. EXECUTE -> perform only explicitly allowlisted, low-risk, reversible actions. Live-site publishing, destructive changes, contractual commitments, pricing changes, client-facing sends, and other consequential actions require human approval until a later policy explicitly permits otherwise.

Every material agent action must be tenant-scoped, logged, attributable to an agent/run, evidence-backed where factual claims are made, bounded by cost/time limits, and recoverable or safely retryable.


INTEGRATION ACCESS RULE

Prefer OAuth, delegated access, API tokens with least privilege, and client-created accounts over passwords. Agent access must be scoped to the minimum permissions required. External write access must be separately classified from read/monitor access. Never give a monitoring agent broad administrator credentials merely for convenience.

SECURITY GUIDELINES FOR THE CLIENT  
- Please do not email or text master passwords if the service allows you to invite a user instead.  
- Do not send banking, payment-card, payroll, or unrelated account credentials.  
- Keep two-factor authentication enabled.  
- If temporary credentials must be used, change or revoke them after the project.  
- If you are unsure how to grant access, tell me the platform name and I can provide instructions.  
- You remain the owner of all client accounts and services.

IF PASSWORD SHARING IS UNAVOIDABLE  
If a platform does not support delegated access and a password is truly required:  
- Use a secure password-sharing method rather than ordinary email or SMS where practical.  
- Use a temporary password if possible.  
- Do not reuse a password from another service.  
- Change the password after access is no longer needed.  
- Never send multi-factor recovery codes unless absolutely necessary for a controlled login session.

BEFORE WORK BEGINS -> INTERNAL CHECK  
- Confirm approved scope requires each requested system.  
- Confirm access works.  
- Confirm client ownership/admin rights remain intact.  
- Confirm current website backup or rollback path.  
- Record hosting/CMS/platform details.  
- Record current analytics/search access before making changes.  
- Do not change ownership, billing, primary account emails, or recovery settings unless explicitly authorized.

ACCESS DURING THE PROJECT  
- Use the minimum permission level necessary.  
- Do not browse unrelated client data.  
- Do not create additional users unless needed and authorized.  
- Do not disable security controls merely for convenience.  
- Document material account/configuration changes.  
- Keep credentials out of ordinary project notes where possible.

PROJECT CLOSEOUT -> ACCESS CLEANUP  
At completion:  
- Confirm the client still has full ownership/admin access.  
- Remove temporary users that are no longer needed.  
- Revoke temporary passwords/tokens.  
- Return/reassign any assets created under a project account when required.  
- Confirm ongoing access only for active monthly-service clients where necessary.  
- Tell the client what access remains and why.
